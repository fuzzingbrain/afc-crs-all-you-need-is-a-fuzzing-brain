# 上下文压缩重设计:可逆驱逐 + 钉死账本

状态:**提案,待评审**
范围:`fuzzingbrain/agents/base.py::_compress_context`(以及 `pov_agent.py` 里的 POV 覆盖)。适用于所有 BaseAgent(SP finder、verifier、POV、seed、direction、report)。

> 英文版:`docs/CONTEXT_COMPRESSION_DESIGN.md`。本文在其基础上,针对我们"**读代码 → 下结论 → 调工具验证**"的循环做了定制化修正(§3.2、§7)。

---

## 1. 现状为什么烂

当前 `_compress_context`(base.py:490):

- 触发:base **每 5 轮**;POV 在 **input ≥ 60K token** 时。
- 保留:`messages[0:2]`(system + 首个 user)+ 尾部 `keep_end`(≥3)。
- 中段**全部** → 拼成文本 → 丢给**廉价模型**(`gpt-4.1-nano` / `claude-haiku-4-5`),`max_tokens=2000` → 整个中段**被替换成一条 summary**(角色 `user`)。

具体失败点:

1. **一个弱模型把整个中段糊成 ≤2000 token。** 中段可能是 50K+ token 的代码阅读、`reach_probe` 轨迹、crash 转储,约 25:1 的暴力压缩。
2. **破坏性、不可逆。** `self.messages = 头 + [summary] + 尾`,**原文永久丢失**。被糊掉的精确 offset / 行号 / 结构体布局 / ASan margin **回不来**——而这些正是 PoV 构造最需要的。
3. **弱模型不知道哪句承重。** 精确事实最先丢。
4. **盲目节奏**(每 5 轮),跟实际 context 大小无关。
5. **一刀切。** "已确认可达""能用的种子""当前最优 PoV 尝试"和垃圾输出一起被糊。
6. summary 以 `user` 角色注入,角色语义乱。

### 文献结论

所有来源高度一致:**summarization 式压缩是长程工具型 agent 里最差的选择**——原话"unpredictable lossiness, structural destruction, blocking cost, and **compression-induced hallucination**"(Beyond Compaction, arXiv 2606.11213)。Anthropic 也只把它列为"需要大量来回时"才用,并强调**先最大化召回**。

state-of-the-art 的替代方案共享两个思想:
- **确定性驱逐老的原始 tool 结果**(Anthropic *context editing* `clear_tool_uses_20250919`:单独 +29%,配 memory tool +39%,**token −84%**,100-turn 评测)。
- **可逆的外部化**(Manus "file system as memory":原始输出丢到文件,上下文里只留轻量引用,按需回取——*"压缩没问题,只要可逆"*)。

链接见 §9。

## 2. 固定骨架(永不压缩)

从代码确认:

| 东西 | 存在位置 | 压缩会动吗 |
|---|---|---|
| system prompt | `messages[0]`(`role: system`,base.py:1046) | **不会**——永远保留 |
| harness 源码 | 拼进 system prompt(base.py:608–649) | **不会** |
| sanitizer 指引 | 拼进 system prompt | **不会** |
| tools | 独立 `tools=self._tools` 参数(base.py:1121),**不在 `messages` 里** | **不会——根本不在可压缩数组内** |

所以压缩唯一能碰的,是 **`messages` 的中段**:首个 user 与近期尾部之间的中间 assistant 轮次和 `tool_call → tool_result` 对。上面这四样是固定骨架,天然出界。

## 3. 目标方案:**可逆驱逐 + 钉死账本**

纯机械,无 summarization LLM,可逆,双 provider 通用。

### 3.1 压缩后的消息布局

```
[0] system   = prompt + harness + sanitizer        ← 固定骨架
[1] user     = 任务 / SP 详情                        ← 固定
[2] LEDGER   = 钉死的关键事实(逐字,单条)           ← 新增,永不驱逐
      ...  中段:老 tool 结果 → 存根  ...             ← 可逆
[.] 近 K 轮,逐字,tool 对成对安全切                   ← 固定近期窗口
tools        = 独立参数                              ← 永不进 messages
```

### 3.2 机制①——老 tool 结果 → 可逆存根(**区分幂等/非幂等**)

这是针对我们循环的**关键定制**。老的 tool 结果(超出近期窗口)分两类处理:

**(a) 幂等读工具**(`get_function_code` / 调用图 / `get_diff`):
它们是压缩的**主要目标**(代码体积大),但**同一输入再调结果一样**。所以存根直接写**重读配方**,**连存盘都不用**:
```
[已移出 · get_function_code("json_parse_ex") · 6.1KB · 需要就重新调用]
```
agent 要用自己会重读,零存储、零风险。

**(b) 非幂等 / 昂贵工具**(`reach_probe` 带某个具体输入、`create_pov`):
跑了 fuzzer/gdb,**重现代价高**,不能靠重调。所以**存盘 + `recall(ref)` 取回**:
```
[已移出 #37 · reach_probe · 8.2KB · recall(37) 取回]
```
原文写进 `results/agent_ctx/<agent_id>/<ref>.json`。**可逆**,不丢。

两类都**保留 assistant 的 `tool_call`**(只替换 result 的 content),保证 `tool_call → tool_result` 结构合法。

### 3.3 机制②——钉死的 LEDGER(承重事实,逐字)

单条消息,**永不驱逐**,装结构化事实。两条来源合并:

**(a) 确定性抽取**——驱逐某个*已知* tool 结果时,自动把关键字段抠进账本(无 LLM):

| 工具 | 抽进账本 |
|---|---|
| `reach_probe` | reached/unreached 函数、`sink_reached`、`asan_margin`、`crash_frame`、`operands`、`first_unreached` |
| `create_pov` | `crashed`、`crash_matches_sp`、最优 margin、崩溃 generator id |
| `create_seed` | 能到达深层代码的种子 hash + 一行说明 |
| `get_function_code` | (可选)agent 标记的缓冲大小 / guard 条件 |

**(b) agent 主动记**——`note(key, value)` 工具,让 agent 把它判断承重的事实钉上去(Anthropic structured note-taking)。同 key 覆盖。**对我们这个循环这不是可选,是必需**(理由见 §7)。

账本示例(逐字、紧凑):
```
## LEDGER
REACH  json_parse_ex=YES(d0)  new_value=YES  | sink: string_add @ json.c:310
FACTS  string 缓冲 = alloc(len+1),大小在 first pass 定;\u 转义越界写 1 字节
SEEDS  sp_a1b2 (6B `"5\u5E0`) -> 到达 310,margin 0
POV    gen#3 crashed=1 @310 ; gen#5 到达未崩 @327
```

账本是驱逐安全的根本:summary 本会毁掉的事实在这里**逐字**存着,而原文还在一个 `recall()` / 重读之外。

### 3.4 机制③——`recall(ref)` 工具(可逆兜底)

返回某个被驱逐(非幂等类)结果的完整原文。极少用,但它是**根治"压完 agent 瞎了"**的安全网,即 Manus 可逆原则的显式化。(幂等读不用它,直接重调工具即可。)

### 3.5 触发与节奏

- **按 token,不按轮次。** input ≥ **高水位**(如模型窗口 50%,或固定如 80K)才驱逐,一次驱逐**最老**的 tool 结果直到回落到**低水位**(如 40%)。摊销式,不再每 5 轮盲压。
- **绝不碰**骨架、账本、首个 user、近 K 轮。
- **纯机械**:无 LLM 调用、不阻塞、无额外花费、无幻觉。

### 3.6 双 provider

- **OpenAI(period-correct:gpt-4.1 / o3 / nano):** 上面全套客户端实现(OpenAI 无服务端等价物)。
- **Claude(current:sonnet/opus/haiku 4.5):** 同一套客户端逻辑照跑保证一致;**额外**可开 Anthropic 原生 `clear_tool_uses_20250919`,让被清 token 不计费、prompt cache 前缀稳定。存根/账本/recall 仍是我们自己的,两边行为一致。

## 4. 保留 vs 驱逐(总表)

**永远逐字(不驱逐):**
- 骨架:system + harness + sanitizer + tools。
- LEDGER(钉死的事实)。
- 首个 user 消息(任务 / SP)。
- 近 **K** 轮(近期窗口,tool 对安全)。

**可逆驱逐(移出,不丢):**
- 幂等代码阅读 → 存根 + **重读配方**(零存储)。
- 非幂等验证结果(`reach_probe`/`create_pov`)→ 存根 + 存盘 + 关键字段进账本。
- 老的中间推理 → 小则留,大则丢(结论进账本后,原始推理不再承重)。

| | 现状(弱模型摘要) | 新方案(可逆驱逐 + 账本) |
|---|---|---|

## 6. 分阶段落地

1. **Phase 1(收益最大、代码最少):** 替换 `_compress_context` 为存根式驱逐——幂等读→存根+重读配方(零存储);非幂等→存盘+`recall()`;token 水位触发。**先不做账本抽取。** 已经严格优于现状:可逆、无损、无幻觉、零成本。
2. **Phase 2:** `reach_probe` / `create_pov` / `create_seed` 的确定性账本抽取(§3.3a 字段)。
3. **Phase 3(对我们其实是必需):** `note()` 工具(agent 记结论);Claude 侧开原生 `clear_tool_uses` 拿计费/缓存红利。

## 7. 为什么特别适配我们的"读代码 → 结论 → 验证"循环

把循环的三类内容对到方案:

| 内容 | 循环角色 | 特点 | 处理 | 合身度 |
|---|---|---|---|---|
| **① 代码阅读** | "读代码" | 大,但**幂等** | 存根 + 重读配方,**零存储** | 极好 |
| **② agent 结论/假设** | "下结论" | 承重,是全链价值 | 进 LEDGER(钉死) | 好(有前提) |
| **③ 验证结果** | "调工具验证" | 结构化,**不幂等/贵** | 存盘 + 抽字段进 LEDGER | 完美 |

**关键洞察**:我们最占地方的**代码阅读是幂等的**,驱逐它几乎零成本(存根写重读配方即可,agent 要用自己重读)。`reach_probe`/`create_pov` 这种贵的验证结果,正好是"抽字段进账本"的教科书场景。

**但有一个真风险,必须正视:**

> "下结论"的价值,必须在**支撑它的代码被驱逐之前**落进 LEDGER,否则就丢了。

- ③ 验证结果有**确定性抽取**兜底 → 稳。
- ② **agent 自由推理的结论**没有自动抽取。它最近的结论在**近期窗口**内(逐字)没事;可一旦超出窗口、又没被 `note()` 记下 → 结论随代码一起没了,只剩"读过这个函数"的存根,得重读再想一遍。

**所以对我们:**
1. **幂等读 vs 非幂等验证必须分开处理**(§3.2)——这是我们循环特有的优化,省掉大量存储。
2. **`note()` 不是可选,是关键**——我们的价值在"结论",必须让 agent 主动钉住结论;只靠确定性抽取只保住"验证结果",保不住"推理结论"。

## 8. 待定 / 风险(评审关注)

- **近期窗口 K、水位 HIGH/LOW** —— 按角色调。POV 需要更大近期窗口(它围着最近几次尝试迭代);finder/verifier 可更紧。
- **被驱逐原文存哪** —— `results/agent_ctx/<agent_id>/` 扁平文件 vs Mongo collection。文件更简单,且贴合 harness/POV artifact 惯例。幂等读根本不存。
- **`recall()` 滥用** —— agent 全 recall 会破坏意义。缓解:每轮 recall 次数上限,或 recall 返回裁剪视图。幂等读引导用重调而非 recall。
- **账本膨胀** —— 确定性抽取在超长 run 可能撑大账本。按 key 覆盖 + 总量上限;最老的低价值 key 老化淘汰(**但淘汰本身必须确定性,不能又摘要**)。
- **tool 对完整性** —— 驱逐 `tool` 结果必须保留其 assistant `tool_call`;存根只换 content。确认 API 接受一个 content 是短存根的 tool_result(接受任意字符串)。
- **OpenAI vs Claude token 计费** —— 客户端路径两边都降真实 token;Claude 原生路径额外把被清 token 计费归零。每次 run 记录开了哪条。
