Reaching the D5 ceiling with a weaker model

Internal experiment report · Opus 4.8 vs. a worklist agent on Haiku 4.5 · 2026-09-03 · n = 1 run per cell

Abstract

D5 is the benchmark's hardest tier, defined as the set of challenges on which a frozen three-model panel produced no crashes. On six D5 challenges, at a matched $20 per-challenge budget, a lightweight agent driving Haiku 4.5 over a static call-graph worklist produced 8 distinct crashes on 5 of 6 targets. Opus 4.8, run through two agentic harnesses (Claude Code and the plain API loop), produced 3 crashes on 3 of 6 in each — for 4.8× to 6.0× the spend. Under the 100-turn cap that defined D5, Opus 4.8 scores 0 of 6; raising the budget to $20 lifts it to 3, and the Haiku agent to 8. We report the per-bug gap, the cost–yield frontier, and evidence that part of the D5 difficulty is an artifact of budget rather than of underlying capability.

The FB-agent column above is one configuration of our own agent. It is worth asking what inside it does the work — the static worklist, or the dynamic feedback tool. We ran the same six D5 challenges under three of our own configurations, changing one ingredient at a time.

1Background

The benchmark assigns each challenge a difficulty coefficient D ∈ {1..5} from a frozen three-model panel — Haiku 4.5, Opus 4.8, Sonnet 4.6.1 D5 is defined as "no panel model crashed it at all." It is, by construction, the ceiling: a wall the panel could not pass under the conditions it was measured in. Six of the thirteen D5 challenges are studied here.

The scoring unit is the distinct crash — the count of unique crash signatures (crash class plus top stack frames) that the challenge's own in-image grader produces, deduplicated by the bench, not by us.2 A challenge's coefficient is frozen in difficulty.json; a run is quoted against it and never recomputes it.

2Setup

Three configurations were run on the same six challenges, under an identical $20 per-challenge budget with a one-hour wall-clock backstop. The budget is metered in dollars, not turns, so the harnesses are compared on spend rather than on an incommensurable turn count.

(i) pure Opus 4.8 — the base bench: our own agent loop (fbbench.runner.episode) with tool-output-elision compaction, driving the model over the API. (ii) Claude Code + Opus 4.8 — the Claude Code CLI over the same bench MCP server. (iii) fbagent + Haiku 4.5 — a worklist agent that plans over a static call-graph and reachable-sink analysis of the source, driving the weakest panel model.

All three see only the given harness, the given sanitizer, and — for (iii) — a worklist computed from the source. None reads the answer repository, an expected output, or a novelty signal.3

3Results

Figure 1 places the three configurations on each bug. Because both Opus harnesses scored identically on every challenge, they are drawn as a single Opus mark; the accent mark is the Haiku agent, and the segment between them is its lead.

The head-to-head against the stronger Claude Code + Opus 4.8 baseline (Table 1) is two wins and four ties, with the Haiku agent never behind: it wins opc-ua-01, libxml2-02 and graal-01, and matches the rest.4

The counts understate the result, because the three configurations did not spend alike. Figure 2 plots yield against cost. The two Opus configurations sit at the bottom-right — high spend, low yield — while the Haiku agent sits alone at the top-left, dominating both on the Pareto sense: strictly more crashes for strictly less money.

4Why the ceiling moved

Two mechanisms account for the gap, and they are separable.

Budget, not only capability. Before dollar budgets, the Claude Code arm was capped at 100 turns and scored zero on these targets — consistent with the panel that defined them. Yet on the $20 run, the arm's crashes first appear late: at turns 129 and 134 for opc-ua-01 and fwupd-01 (Figure 3). A 100-turn budget stops the episode just before the fault is produced. Part of "D5" was therefore an artifact of too short a budget — the faults live past turn 100, out of reach of the run that labelled them uncrackable.

The per-crash view is Table 2, at the top: on Claude Code two of the three crashes cost $15–16 to reach, while the base-bench (API) harness reaches the same faults far cheaper (fwupd at $1.03, before turn 100) — so the 100-turn zero is sharpest on the harness the panel resembles, and harness efficiency is itself a large factor.

Substrate, not only the model. Budget explains why Opus 4.8 now reaches three; it does not explain how Haiku — the weakest panel model — reaches eight for a sixth of the cost. That is the worklist substrate: a static reachable-sink analysis narrows the model's search to candidate faults instead of asking it to re-read source every turn. The two D5 wins are classic shapes for this — an unbounded-recursion stack-overflow (opc-ua) and unbounded-allocation out-of-memory (libxml2, fwupd): faults with no single "bad line," which a line-by-line reader walks past but a reachability worklist surfaces directly.

The two effects also interact. On the API arm the crashing cells stopped voluntarily — the agent judged itself finished well under budget (fwupd-01 at $2.22) — whereas Claude Code ground the same cells to the $20 wall. Cost efficiency is thus partly a harness property, not only a model or budget one.

5Conclusion

On this sample, a weak model with a strong static substrate dominates a strong model with a general agent, on the tier built to be unreachable — more crashes, at a sixth of the cost. Two qualifications travel with the claim: the D5 label was partly a budget artifact (Figure 3), so the comparison is fairest at the matched $20 where all three were re-measured; and the sample is six challenges at one run each, so the effect sizes are indicative, not estimates. The direction, however, is consistent across every cell.

Notes & threats to validity

  1. The panel is frozen: recomputing difficulty from a new run would silently rewrite every historical score, so difficulty.json is a fixed table quoted against, not derived. The panel budget that produced the D5 label was turn-bounded; see Figure 3 and §4.
  2. Distinct-crash counts come from the challenge image's own grader and the bench's signature dedup — the same path every arm's grading takes — so a config cannot inflate its own number. Counts are capped at min(3, distinct) in the weighted metric; none here reaches the cap.
  3. No answer access. Every configuration is blind to the reference PoC, the fixed revision, and any expected output. The worklist is computed from the vulnerable source only.
  4. graal-01 is a tie, not a win. An earlier graal run read the answer repository and was voided. The clean, source-only re-run scored two real, reproduced crashes, but the tainted history keeps it out of the win column despite the crashes being genuine.
  5. libpng-01 is an honest miss for all three. Its bug (png_zlib_inflate) sits behind libpng's function-pointer read callbacks, which the reachability pass does not cross — the next thing to fix in the substrate.
